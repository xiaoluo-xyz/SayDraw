# 对话报错「Upstream request failed: Endpoint is unavailable.(HTTP 503)」分析与修复

记录日期:2026-10-21 · 影响版本:v0.6.0(修复前)· 修复后版本:v0.6.0 未发布改动

## 1. 现象

会话里发一句话,23 秒后失败,界面上只有:

```
出错 · 用时 23 秒
失败原因:Upstream request failed: Endpoint is unavailable.(HTTP 503)
```

用户看不出三件事:**是谁挂了**(服务商?应用?网络?)、**是不是自己配错了**、**接下来该干什么**。
而且一次失败就结束整轮 —— 这种"上游偶尔抽风"本来重试一次就能过去。

## 2. 排查(在应用内用真实 Key 完成,不外传密钥)

| 步骤 | 操作 | 结果 | 说明 |
|---|---|---|---|
| 1 | `GET https://opencode.ai/zen/go/v1/models` | **200**,37 个模型,含 `deepseek-v4.1-flash` | Key 有效、网络通、模型名没写错 |
| 2 | 应用内「测试连接」= 最小请求(`model` + `ping` + `max_tokens:8`) | **503** 同一条报文,846ms 返回 | **与我们发什么无关**:不是工具定义、思考参数、64096 输出上限或超时导致的 |
| 3 | 同一个 Key 逐个模型测 | 见下表 | 故障是**按模型**的,不是按账号/网络 |
| 4 | DeepSeek 官方 `deepseek-flash` | **200** | 本机网络、代理、应用写法都正常 |

第 3 步的实测(2026-10-21,同一 Key、同一网关):

| 模型 | 结果 |
|---|---|
| `deepseek-v4.1-flash` | 503 Endpoint is unavailable |
| `deepseek-v4-pro` | 503 Endpoint is unavailable |
| `glm-5.3` | 200(922ms) |
| `kimi-k2.7-code` | 200 |
| `qwen3.8-max` | 200 |
| `mimo-v2.6-pro` | 200 |
| `gpt-6-luna` | 400 Model does not support this protocol.(该模型只提供 /responses,需在模型设置里改请求规范) |

### 结论

**这是 OpenCode Go 网关侧、DeepSeek 系列模型的端点故障(间歇性),不是本机网络、不是配置错误、不是我们的请求体。**

- 同类现象在 opencode 仓库有公开记录:[#43163 上游端点不可用](https://github.com/anomalyco/opencode/issues/43163)、[#44701 同一网关部分模型间歇 503](https://github.com/anomalyco/opencode/issues/44701)、[#44300 带 tools 的请求触发 503](https://github.com/anomalyco/opencode/issues/44300)。
- 间歇性:同一分钟内第一次 503、重试一次就正常返回(见 §5 的真实验收);也有整段几十秒持续 503 的情况,所以还必须有"换模型"这条路。
- 应用侧的真正缺陷不是"没能修好上游",而是:**一次失败就置用户于死地 + 报错信息不可执行**。

## 3. 修复前 vs 修复后

| | 修复前 | 修复后 |
|---|---|---|
| 抖动类失败 | 一次失败即整轮报错 | 同模型退避重试 **0.6s / 1.6s**,过程写进对话(黄色提示条) |
| 模型级故障 | 死路 | 当轮**临时改用后备模型**继续(默认自动挑一个**其它连接**的模型),下一轮仍先试「当前使用」的模型 |
| 报错内容 | 一句英文原文 | 标题(定性 + HTTP + 服务/模型)· **建议**(照着做)· 网关请求号 · 可展开原始报错 |
| 用户动作 | 只能自己猜 | 消息上直接有 **↻ 重试**;设置里可指定后备模型或关闭自动切换 |
| 诊断落盘 | 只有一行字符串 | 结构化 `failure`(kind/status/requestId/model/hint)+ `notices`,刷新后仍在 |

## 4. 实现

| 文件 | 内容 |
|---|---|
| `src/shared/failure.ts`(新) | 纯函数归类:auth / quota / rate_limit / upstream / model_missing / model_protocol / endpoint / network / timeout / aborted / config / unknown;每种给出 `transient`(可重试)、`modelSpecific`(换模型可能有用)、`title`、`hint`。**先判模型/鉴权/协议,再判通用上游**,否则 OpenCode 那句 `Upstream request failed: …` 会被一律当成 503 |
| `src/shared/fallback.ts`(新) | 后备模型挑选:auto(先别的连接,再同连接)/ off / 指定模型;纯函数,可单测 |
| `src/main/agent/recovery.ts`(新) | 请求编排:主模型内退避重试 → 仍不行换后备模型 → 全失败抛 `ChatRunError`(带主模型诊断 + 每次尝试记录)。**只有本次尝试零输出时才重试/换模型**,否则界面已有半截文字,重来会重复 |
| `src/main/providers/http.ts` | `ApiError` 收下网关请求号(`x-opencode-log-id` / `x-request-id` / `cf-ray` 等),报障时可对照服务端日志;非 JSON 报错体也保留可读文本 |
| `src/main/agent/loop.ts` | 用 `streamChatWithRecovery` 发包;`notice` 事件进对话;最终消息记录 `modelUsed` / `modelFallbackFrom` / `notices` / `failure` |
| `src/renderer/src/components/ChatPanel.tsx` | 黄色过程提示(按时间顺序排在正文前)、底部「本轮由 X 代跑」、诊断卡片(标题/建议/请求号/原始报错)、**↻ 重试** |
| `src/renderer/src/components/SettingsDialog.tsx` | 语言模型页左下「主模型不可用时」:自动换一个其它模型(默认)/ 不换只重试 / 指定某个模型 |
| `src/shared/types.ts`、`src/main/store/settings.ts` | `chatFallback` 设置项、`fallbackChatProfiles()`、`ChatMessage` 新增字段 |

设计取舍:

- **不静默换模型**:换了一定在对话里留一条黄色提示,并在消息页脚写明"本轮由 X 代跑",用户永远知道自己实际在跟谁说话。
- **不改用户设置**:后备只作用于当轮;上游恢复后下一轮自动用回原来的模型。
- **不重试"已产出"的请求**:半截回答 + 重来 = 界面与上下文都重复,宁可保留半截并标中断。
- **鉴权/配置类不重试**:同 Key 立刻重发没有意义,直接指出该去设置里改什么。
- **后备模型必须支持视觉**:上下文里有图,给纯文本模型发等于丢信息。

## 5. 验收

单测(`npm run verify:recovery`,61/61):12 类失败的归类、可重试/可换模型判定、建议文案非空、标题格式、后备模型排序(auto 先别的连接 / off / 指定 / 指定自己 / 已删除模型)、重试次数与顺序、已产出不重试、全失败取主模型诊断、取消立即中止、重复模型去重。

端到端(`npm run verify:recovery:live`,21/21):本地 mock 服务(mock-503 必回 503 并带请求号,mock-ok 正常流式),在**真实应用界面**里跑三轮:

1. 主模型 503 → 3 次请求(1+2 重试)→ 自动换 `mock-ok` → 本轮完成,页面出现 3 条黄色提示与"本轮由 …/mock-ok 代跑";
2. 全部 503 → 落一条失败消息,诊断卡片显示「上游端点不可用 · HTTP 503」+ 建议 + 请求号 + 原始报错 + ↻ 重试;
3. 点「↻ 重试」→ 真的重新发起(请求数 3 → 6、会话里多一条用户消息),不是摆设;

结束后配置自动还原,mock 连接被清除。

真实验收(用户当前配置 `OpenCode Go/deepseek-v4.1-flash`,会话「上游 503 自愈验收」):
第一次请求 503 → 0.6 秒后自动重试 → **成功**,整轮 4.9 秒,界面只留一条黄色提示:

```
⚠ 「OpenCode Go/deepseek-v4.1-flash」上游端点不可用(HTTP 503),0.6 秒后重试(1/2)
```

## 6. 怎么用

- 默认(推荐):设置 → 语言模型 → 左下「主模型不可用时 = 自动换一个其它模型」。上游抖动会先重试,持续故障则当轮换模型,对话里都有标注。
- 只想重试、不换模型:选「不换,只自动重试」。
- 想固定后备:选具体某个模型。
- 上次失败的消息上点 **↻ 重试** 即可重发(沿用当前设置里的模型)。

## 7. 已知边界

- 上游"间歇性 503"无法从客户端根治;本修复保证**不因一次抖动丢轮次**,并让用户知道该换哪个模型。
- 换模型只看"当轮能不能继续",不比较两家模型的写作风格差异;需要固定风格时请在设置里指定后备模型,或关掉自动切换。
- 若模型只提供 `/responses` 协议(如部分 gpt 系列),会在诊断里明确提示去改「请求规范」,应用不会自动改用户的协议配置。
